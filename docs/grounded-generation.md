# 接地生成（G2）: NLIによる前提補正（トークン生成なし）

純粋な retrieval では「近いチャンクの値をそのまま返す」ため、質問の前提が異なっても同じ肯定文を返してしまう。例：「君はRAGで生成をしているのか？」に対し、正しくは「いいえ、生成はしていない」と前提を否定して答えたい。これを **トークン生成なし** で実現するのが G2。

## 仕組み

返答モードで `generate=true`（UIの「接地生成」トグル ON）かつ、選ばれたチャンクが「極性を持つ主張」（`assertion` と `stance` を持つ）のとき：

1. **NLI(前提 = ユーザー質問, 仮説 = チャンクの `assertion`)** を実行（`nli.ts`）。
2. **entailment（質問がその主張を前提している）かつ `stance === "deny"`（チャンクの事実がその主張を否定）** なら「偽の前提」。
   - 応答 = **閉じた否定オープナー（言語別・`NEGATION_OPENER`）＋ チャンクの値（コピー）**。例：「いいえ、そうではありません。」＋「近い。でも RAG は…生成段がなく、回収＝返答。」
3. それ以外は値をそのまま返す（as-is）。

**「完全」制約の遵守**：操作は「閉じたオープナーを前置＋既存の値をコピー」だけ。**新規トークンは生成しない**。トレースに NLI ラベル・スコア・操作（`negate-correct`/`as-is`）を出し監査可能。

## NLIフレーミングの選定（実測）

質問を仮説にすると機能しない（NLIは宣言文が前提）。4通り試し、**NLI(premise=質問, hypothesis=主張の宣言文)** が最良：偽前提の質問→entailment、中立質問→neutral とクリーンに弁別。

- モデル：`onnx-community/multilingual-MiniLMv2-L6-mnli-xnli-ONNX`（小型 L6・多言語）。Transformers.js で動作、**fp32 で決定的**（q8はリランカー同様に不安定なので不可）。1ペアずつ採点。

## 対象クレーム

偽前提が起きやすい少数のクレームにのみ `assertion`/`stance="deny"` を付与：`who-1`（LLMか）、`mech-rag-a`（RAGで生成か）、`code-1`（コード書けるか）、`code-bug-a`（バグ直せるか）、`phil-1`（意識/理解があるか）、`var-attention`（attention KVか）。

## 実測（実コーパス／API経由）

- RAG・コード・意識の偽前提質問（各3言語＝9件）：**9/9 で negate-correct**（「いいえ、そうではありません。／No, that's not the case. ／不，并不是这样。」＋既存値）。
- 中立質問（「仕組みを教えて」等）：as-is（誤補正なし）。
- 接地生成 OFF：素の retrieval 値を返す（同一入力で ON/OFF を比較でき、この作品のテーゼ＝生成の有無で会話がどう変わるかを実演）。

## 拡張・安定化（v2）

- **複数フレーズの主張（`assertions: string[]`）**：質問の言い回し差に強くするため、1クレームに複数の宣言文を持たせ、NLI を各文に対して実行し**最大 entailment** を採る。これで「君はLLMなの？」（以前は neutral）が全3言語で entailment→補正されるようになった（0.99/0.96/0.98）。
- **質問の正規化**：NLI 前に末尾の疑問記号を除去し、質問を宣言文寄りにして NLI を安定化（`normalizeForNli`）。トークン生成ではなく NLI 入力の整形のみ。
- **affirm-confirm 操作**：`stance="affirm"` のクレームで、質問が真の前提を含む（entailment）とき、肯定オープナー（「はい、その通りです。／Yes, exactly. ／对，正是如此。」）＋既存値を返す。例：「君は検索で返答を選んでるの？」→ affirm。中立の how 質問は as-is のまま（誤 affirm しない）。

## 融合（fusion, v3）

**セグメント駆動**の融合（トークン生成なし・両値コピー）：

1. クエリを接続詞（「と」「、」「and」等）で**セグメント分割**（`compoundSegments`）。2つ未満なら融合しない。
2. フルクエリのランキング（広めの窓・top-8）を cross-encoder（キーワード列キー）でゲートし、`FUSE_MIN=0.5` 以上の候補を「関連チャンク」として確保。
3. **各セグメントを、その関連チャンクのうち埋め込み類似度が最大のものへ割り当てる**（セグメント→チャンクの逆写像。単語セグメントが別チャンクのキーに含まれる語で誤対応するのを避けられる）。
4. 異なるチャンクに割り当たった2つ以上のセグメントを**クエリ順**に並べ、各非先頭パートを**入力から抽出した当該セグメント**で「{話題}については、／As for {topic}, ／至于{topic}，」と流暢に前置（助詞のみ閉じた糊）。

- 例：「仕組みと既存の似た手法を教えて」→「…「次のセリフ」。**既存の似た手法については、**あるよ。retrieval-only chatbot…」（"既存の似た手法" は入力からの抽出）。汎用接続詞「ちなみに、」は使わない。
- 単一話題・同一話題は融合しない。トレースに `fusedWith`。

> 注：この過程で埋め込みモデルを **fp32** に変更した。q8 量子化は onnxruntime-node 上で非決定的（同一テキストが実行ごとに異なるベクトルになり、検索スコア・信頼度ゲート・融合が不安定化）。fp32 で再現性を確保。結果、埋め込み・リランカー・NLI の3モデルが fp32 となり初回DLは重い（→ モデル軽量化は別途検討）。

- 例：「仕組みと既存の似た手法を教えて」→ `mech-1`（仕組み）＋ `mech-existing`（既存手法）を結合。
- 単一話題は結合しない。同一話題の2件（例「天気どう？」の weather 系）も**異話題制約で結合しない**（冗長回避）。
- 保守的な発火：混在話題クエリは各キーワード列キーへのゲートスコアが薄まりやすく、両方 ≥0.5 になる強い複合質問でのみ結合する。

## 既知の限界

- **NLIは質問の言い回しに敏感**：複数フレーズ化で改善したが、一部（特に中国語の一部言い回し）は neutral になり as-is にフォールバックする（as-is 自体は妥当な答えなので破綻はしない）。
- **retrieval が極性チャンクを surface できないと補正できない**：極性質問がそのチャンクを top に出す必要がある（natKey に前提質問の語を含めると改善）。
- 主張は「単一の命題」に絞る必要がある（連言は entailment が弱まる）。
- 次段：融合（複数チャンク結合）、焦点合わせ、より頑健な前提抽出。
