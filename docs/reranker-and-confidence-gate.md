# ランキング ＋ 信頼度ゲート（v1.5）

多言語化 v1 で「言語ルーティングは正しいが、bi-encoder 単段の選択精度が一部（特に中国語の言い換え）で甘い」という弱点が見えた。これを、生成を足さずに retrieval の質で解消するのが v1.5。

## 実験：リランカーは必要か、キー品質で足りるか

3言語 × 12〜15トピックのラベル付き評価（言い換えクエリ＋コーパス外）で4条件を比較した：
{キーワード列キー / **自然文キー**} × {bi-encoderのみ / cross-encoderリランク}。

- **キー自然文化が効く**：bi-encoder の top-1 正解率が keyword列キーの 86% → 自然文キーで 92% に向上。
- **リランカーはランキングを改善しない**（同等〜悪化）。→ *精度目的ではリランカーは不要*。
- **ただしコーパス外分離はキーワード列キー＋リランカーだけがクリーン**。自然文キーは（bi でも rerank でも）OOC分離を悪化させる（自然文クエリのOOCが自然文キーと似るため）。

結論：**ランキングは自然文キー＋bi-encoderが最良。リランカーの唯一の価値はコーパス外の信頼度ゲート**。この2つを組み合わせたのが下記の構成（案B）。

## 構成（案B）

1. **Stage 1 — ランキング（bi-encoder, `embed.ts`）**: クエリを多言語埋め込みし、各チャンクの **`natKey`（自然文キー）** との cosine 上位を取る（言語・話者フィルタ込み）。リランカーでの並べ替えは行わない。
2. **Stage 2 — 信頼度ゲートのみ（cross-encoder, `rerank.ts`）**: 上位 `GATE_CANDIDATES` 件の **`key`（キーワード列キー）** を `(query, key)` で採点し、その最大値を信頼度とする。順位は変えず、拒否判定だけに使う。

各チャンクは2種類のキーを持つ（`corpus.ts`）：`natKey`＝ランキング用の自然文、`key`＝ゲート用のキーワード列。ゲートにキーワード列を使うのは、コーパス内/外の分離がキーワード列の方が圧倒的に良いため。

## モデル選定

`Xenova/bge-reranker-base`（多言語 XLM-RoBERTa cross-encoder, Transformers.js/ONNX）。
- `onnx-community/gte-multilingual-reranker-base` は transformers.js が未対応（`Unsupported model type: new`）。

### 重要な実装上の落とし穴（実機で判明）

- **量子化(q8/int8)は使用不可**: onnxruntime-node 上で数値的に不安定。同一入力に対して非決定的なスコア（例：0.07, 0.07, 0.99）を返し、無関係キーに誤って高スコアを付ける。→ **fp32 必須**（fp16 は CPU 実行が非対応でロード失敗）。代償として初回ダウンロードが大きい（一度キャッシュされれば以後は速い）。
- **バッチ＋パディングも不可**: 複数候補を1バッチで採点すると、パディングが相互にスコアを歪め、バッチ構成次第で同一ペアのスコアが変わる。→ **1ペアずつ（バッチサイズ1）で採点**して決定的にする。候補数は `RERANK_CANDIDATES=10` に抑え、逐次フォワードのレイテンシを許容範囲に保つ。

## 信頼度ゲート（graceful refusal）

キーワード列キーに対する fp32 bge-reranker-base のスコアは、コーパス内一致 ~0.1–0.99、明確なコーパス外 ~0 と分離する。返答モードで最良スコアが `GATE_MIN_SCORE=0.03` 未満なら、無関係チャンクを貼らず、その言語の `limit-1`（「近いキーがないと的外れが勝つ」）を返し、トレースに `lowConfidence` を立てる。連鎖（predict-user）モードでは拒否しない（探索的なため）。

## cosine レスキュー（誤拒否の一方向救済）

リランカーは短いキーワード列キーに対しまれに低スコアを返し、正当なクエリを誤拒否する（例：「What do you mean by KV?」conf≈0）。これを、bi-encoder cosine を**一方向だけ**使って救う：

- ゲートが拒否判定でも、ランキング top-1 の**生の cosine が `RESCUE_COS=0.7` 以上**なら、最近傍のコーパス要素が明確に近い＝低スコアはフレークと見なし、**拒否を取り消して答える**。
- **OOC 検出には使わない**（cosine は in/out が重なり不向き）。判定を動かす向きは「拒否→応答」のみ。`RESCUE_COS` は OOC の cosine 重なり帯（実測 ~0.5–0.56）より十分高く設定。

## 実測（実コーパス 52クレーム／API経由）

3言語 × 15トピックの言い換えクエリ＋各言語コーパス外4件：

| | 案B（ゲートのみ） | ＋cosineレスキュー |
|---|---|---|
| コーパス内 top-1 正解率 | 42/45 = 93% | **43/45 = 96%** |
| コーパス外 拒否率 | 11/12 = 92% | 11/12 = 92%（不変） |

cosine レスキューは KV の誤拒否1件だけを救済し（発火1回）、OOC漏れは増えていない。自然文キーのランキング精度とキーワード列キーの OOC 拒否を両立しつつ、リランカーのフレークによる誤拒否も抑えられた。残る誤りは短文埋め込みの意味衝突（「Hey there!」→別れ、「君の正体は？」→挨拶）で、ゲートではなくランキング側の課題。

## 既知の限界

- 短文埋め込み由来の意味衝突が少数残る（例：「Hey there!」→ 別れの `bye-a`、「今天股市怎么样？」→ 挨拶へ漏れ）。
- ゲートに使う短いキーワード列キーに対し、リランカーがまれに低スコアを返し**正当なクエリを誤拒否**することがある（例：「What do you mean by KV?」）。1/45程度。
- q8量子化のリランカーは非決定的（同一入力に 0.07,0.07,0.99 等）＋誤高スコア → **fp32必須**（fp16はCPU非対応）。バッチ＋パディングもスコアを歪めるため **1ペアずつ採点**。
- 次段：NLIベースの操作分類（融合/編集型の接地生成）で "how" 系の衝突や誤拒否を更に減らせる見込み。
